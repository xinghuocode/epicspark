# EpicSpark · 历史场景实时生成游戏 — 架构与使用文档

> 目标引擎：**Unity 2022.3.62f3c1（URP 14.0.12）**
> 设计依据：外置设计文档（两个仓库分支里的 `ARCHITECT.md` 已按用户要求作废，不参与实现）
> 运行依赖：**零第三方包**（无 Newtonsoft / System.Text.Json / HttpClient / glTFast），全部使用 Unity 原生 API 与 C# 8 语法。

---

## 1. 这是什么

玩家输入一个历史事件（如「攻占巴士底狱」），游戏在数十秒内**实时生成**一个可自由行走的 3D 历史场景：
区域与道路先在灰盒里规划出来，再从美术资产库里检索匹配的模型落位，库里没有的资产由 AI 现场生成；
玩家走进场景里的**传送锚点**推进剧情，进入下一个场景（新场景即时生成，走过的场景复用）。

整条流水线由四层 Agent 组成，**每一层都有确定性离线兜底**：没有 API Key 也能完整游玩，只是剧情与资产退化为本地规则生成。

## 2. 快速开始

1. 用 Unity **2022.3.62f3c1** 打开本工程（首次导入约 2–5 分钟，会导入 43 个 GLB 与 26 个知识语料文件）。
2. 打开场景 `Assets/Scenes/EpicSpark.unity`（已生成，并已写入 Build Settings）。
3. 直接点 Play。
   - **未配 API Key**：以离线确定性模式运行，可完整体验。
   - **想用真实大模型**：见本章末尾的 Key 配置。
4. 标题界面输入事件或点推荐按钮 → 等待场景生成（约 10–20 秒，含加载动画）→ WASD 走进锚点推进剧情。
   已有存档时标题界面会多出 **「继续上次存档」** 按钮，读档会恢复事件、游戏内时间、场景与玩家状态。

### 配置 API Key（三种方式，优先级从高到低）

| 方式 | 做法 |
|---|---|
| **游戏内设置界面** | 标题界面点「设置 API Key 与模型」，或进入游戏后按 **F10**。可填 Key / Base URL / 对话模型 / 向量模型 / 文生图模型 / 单图生 3D 模型，保存后**立刻热生效**（并写入 PlayerPrefs） |
| 环境变量 | `EPICSPARK_API_KEY` |
| 场景内 Inspector | 选中 `EpicSpark` 对象，在 `GameBootstrap` 组件里填 `Api Key`、`Base Url`、`Chat Model` |

Key 为空 / 勾选 `Force Offline` / 设置界面打开「离线」时：`LlmService.HasRemote == false`，**不会发出任何网络请求**。

### 设置界面细节

- 打开方式：标题界面「设置 API Key 与模型」按钮，或游戏内 **F10**（再按一次关闭）。
- 可改 8 项：`API Key`、`Base URL`、`对话模型`、`向量模型`、`文生图模型`、`单图生 3D 模型`、`请求超时(秒)`、`max_tokens`；
  另有「离线」「知识库远端向量」两个开关，以及 `Gitee AI / DeepSeek 官方 / 本地 LM Studio` 三个预设。
- **「测试连接」** 会当场发一次真实请求，分别显示对话与向量是否成功、耗时、向量维度或错误原因，
  不用开一局游戏就能确认 Key / 端点 / 模型名是否匹配。
- 点「保存并应用」后：LLM 换客户端（后续请求立即用新 Key/端点/模型）、知识库丢弃旧客户端下次检索重建、
  资产生成配置同步并落盘；进行中的旧请求不受影响。
- 「恢复默认值」只填默认值到界面；「清除本机配置」会删掉 PlayerPrefs 里保存的全部项，重启后回落到 Inspector / 环境变量。
- 存储位置：PlayerPrefs（Windows 为注册表 `HKCU\Software\Unity\UnityEditor\DefaultCompany\epicsparktest4`），日志里 Key 会打码显示。
  这是本机明文存储，**不要把带 Key 的机器共享出去**；正式发行应改用服务端换取临时凭证。

### 知识库为什么默认不走远端向量接口

知识库有 **600 个事件 / 3606 个文本块**。用远端 `/embeddings` 建索引意味着把这 3606 个块**全部**分批嵌入：
`3606 ÷ 16 ≈ 226 次 HTTP 请求`，每批几百毫秒起 ⇒ 首次检索要 **数分钟**，而且期间没有任何进度提示，看起来就是"卡住"。
所以默认用进程内本地向量（1024 维特征哈希，约 1–2 秒），「知识库远端向量」开关默认关闭。
确实需要远端语义检索时再打开，并做好等几分钟的准备。

> 踩坑记录：早期版本只要填了 API Key，知识库 `Auto` 模式就会自动走远端嵌入，
> 于是"填完 Key 开局"必然卡在「检索历史知识库」这一步。现已改为默认本地，并给所有远端步骤加了硬超时。

## 3. 四层 Agent 架构

| 层 | 职责 | 代码位置 | 契约 | 离线兜底 |
|---|---|---|---|---|
| **剧情&核心 Agent** | 事件 → 五幕剧情（开端/冲突/转折/高潮/结局）；产出 `StoryTurn`，内含 SceneSpec（锚点、NPC、道具、流程步）、叙述、结局 | `Scripts/Story/` | `IStoryAgent` | `DeterministicStoryBuilder`：6 套时代语料 × 7 个场景模板 × 五幕推进，sceneId 稳定可复现 |
| **灰盒 Agent** | SceneSpec → `GrayboxPlan`：区域、道路、NPC 路线、可检索语义槽位、出生点 | `Scripts/Graybox/` | `IGrayboxAgent` | `GrayboxPlanner`：关键词加权分类 8 类场景、网格切分（区域闭合互不重叠）、主/横/支路网、8–20 个语义槽 |
| **搭建 Agent** | 语义槽 → 模型库检索 → 分类、尺寸、旋转、落位；缺口交给资产生成 | `Scripts/Build/` | `IBuildAgent` | `ModelCatalog`（本地向量 + 中英双语概念匹配）+ `BilingualMatcher` |
| **资产生成 Agent** | 缺口资产：文生图 → 抠图 → 单图生 3D → GLB 落盘并热注册 | `Scripts/AssetGen/` | `IAssetGenerator` | 未配 Key 或远端失败时，克隆库内最接近条目并写 `runtime_library.json` |

横切能力：

- `Scripts/Core/` — 全部 DTO 与接口契约（`EpicSparkTypes.cs` / `EpicSparkContracts.cs`）、行为日志与游戏内时间（`GameLog`、`GameClock`）。
- `Scripts/Loading/` — **自研 GLB 运行时解析器**（Unity 无原生 glTF 导入器）、边缘提取、灰盒线框渲染、场景装配、加载动画、场景缓存复用。
- `Scripts/AI/` — OpenAI 兼容 HTTP 客户端（`UnityWebRequest` + `Task.Yield` 轮询 + 取消即 `Abort`）、工具调用；`AI/Knowledge/` 为进程内 RAG（600 事件 / 3606 文本块）。
- `Scripts/Player|Tools|Anchors|Npc|UI/` — 第一人称控制、枪/挎包工具、传送锚点、NPC 血条与对话、HUD/叙述/阶段遮罩/容忍度滑块。

## 4. 一次游玩的完整时序

```
输入事件
  │
  ├─ KnowledgeService.GetContextAsync      检索历史知识（600 事件 RAG），同时给出起始年份
  ├─ GameClock.Reset(year)                 1793年7月14日 08:30 这样的游戏内时钟
  ├─ Story.BeginAsync                      剧情&核心 Agent → StoryTurn（五幕，首场景 activeSceneIndex）
  │
  └─ 进入场景 EnterSceneAsync
       ├─ SceneCache.Contains(sceneId)? ── 是 ── 复用：激活旧场景、刷新锚点/NPC、立即显影（跳过灰盒与搭建）
       │                                  否
       ├─ Graybox.PlanAsync               灰盒 Agent：区域/路网/槽位/出生点
       ├─ Build.BuildAsync                搭建 Agent：逐槽检索模型库；未达标 → AssetGen.GenerateAsync
       ├─ SceneAssembler.AssembleAsync     解析 GLB → 灰盒线框 + 模型（先平面材质）+ 锚点 + NPC
       └─ SceneLoadingSequence.PlayAsync   加载动画：线框全部显影 → 由近及远逐块换成真实贴图 → 标签出现
  │
  └─ 游玩中：走动 / 互动 / 开枪 / 与 NPC 对话 / 调容忍度滑块
       │
       └─ 走进传送锚点 AnchorRouter.AnchorEntered
            ├─ GameLog.Record("enter_anchor")，GameClock.AddDelta(anchor.timeDelta)
            ├─ Story.ContinueAsync(StoryContinueRequest)   剧情&核心 Agent 推进一幕
            └─ 触发结局(gameOver) 或 进入下一个场景（递归回到 EnterSceneAsync）
```

生成期间玩家输入被禁用、阶段遮罩显示当前阶段（检索 → 灰盒 → 搭建 → 显影）；若此时玩家又踩到锚点，请求会排队（`GameDirector.DrainPendingAnchor`），不会丢事件。

## 6. 核心契约（`Scripts/Core`）

所有模块只依赖 `EpicSparkContracts.cs` 里的接口与 `EpicSparkTypes.cs` 里的 DTO，便于替换实现：

- `ILlmService` — `HasRemote` / `CompleteAsync` / `CompleteWithToolsAsync` / `EmbedAsync`
- `IStoryAgent` — `BeginAsync(userEvent, knowledgeContext, ct)` / `ContinueAsync(StoryContinueRequest, ct)`
- `IGrayboxAgent` — `PlanAsync(GrayboxRequest, ct)`
- `IBuildAgent` — `BuildAsync(BuildRequest, ct)`
- `IModelCatalog` — `IsLoaded` / `LoadAsync` / `AllAsync` / `FindBestAsync` / `RegisterRuntimeEntry`
- `IAssetGenerator` — `GenerateAsync(prompt, category, ct)`
- `IKnowledgeService` — `GetContextAsync` / `SearchAsync`
- `GameEvents` — 统一事件总线：`PhaseChanged` / `NoticePosted` / `NarrativePosted` / `ActionRecorded` / `NpcHealthChanged`
- `Services` — 全局服务定位器（Llm / Story / Graybox / Build / Catalog / AssetGenerator / Knowledge / Save）

关键 DTO：

- `SceneSpec` — sceneId、sceneName、era、区域描述、`anchors[]`、`npcs[]`、`props[]`、`flowSteps[]`
- `GrayboxPlan` — regions / paths / slots / npcPaths / spawnPoint
- `PlacedAsset` — slotId、modelId、世界坐标、缩放、旋转、是否现生成
- `StoryTurn` — narrative、scenes[]、activeSceneIndex、gameOver、endingSummary、endingAchievement

## 7. 坐标与资产约定

- **平面坐标**：灰盒与搭建阶段用 `(x, y)` 平面；装配时映射为世界 `(x, height, z)`，即平面 y → 世界 z，地面高度 0。
- **模型归一化**：所有库内模型归一化为单位立方体（±0.5），`pivot` = `bottom`（原点在底面中心）或 `center`。
- **放置**：搭建 Agent 按类别给出尺寸区间（如建筑 8–14、道具 0.8–2），再乘以槽位缩放。
- **GLB 加载**：`GlbModelLoader` 自研解析（12 字节头 → JSON chunk → BIN chunk → POSITION/TEXCOORD_0/uint32 索引），
  做 **右手系 → 左手系的 x 翻转 + 三角形绕序反转**，`RecalculateNormals`，内嵌 PNG 用 `Texture2D.LoadImage`，
  材质用 URP/Lit；按文件名缓存。
  文件查找顺序：绝对路径 → `StreamingAssets/Models/` → `persistentDataPath/EpicSpark/generated/`，
  因此运行时生成的资产与内置资产走同一条加载路径。

## 8. 容忍度滑块（语义不可改）

界面上是「容忍度」，取值 `sliderValue ∈ [0,1]`：

- `tolerance = 1 - sliderValue`
- 复用门槛 `requiredSimilarity = sliderValue`
- `sliderValue = 0` → 门槛 0，**任何相似度都复用库内资产**（最省、最快）
- `sliderValue = 1` → 门槛 1 且启用 `AlwaysGenerate`，**连相似度恰好 1.0 也不复用**，强制走生成
- **资产生成 Agent 产出的资产直接使用，不再做容忍度判定**（否则会无限生成）

美术库 prompt 是英文、灰盒语义是中文，离线向量检索几乎不可能命中，因此 `ModelCatalog` 的相似度取
`max(余弦相似度, BilingualMatcher 概念分)`；概念分来自 43 个资产的双语概念表 + 条目中文名称覆盖率。

## 9. 场景复用

- `SceneCache` 以 `sceneId` 为键保留已装配场景（`root.SetActive(false)` 挂起，保留模型与材质）。
- 再次进入同一 `sceneId`：不重走灰盒与搭建，直接激活 + `RevealImmediate`（无加载动画），
  并通过 `SceneAssembler.RefreshActors` 重建**新的**锚点与 NPC（因为新流程带来不同剧情单位）。
- 剧情 Agent 的 sceneId 是稳定的：`s_<事件哈希>_<幕序号>_<模板码>[_<访问次数>]`，同一事件同一幕永远同一 id。
- 外部入口：`GameDirector.EnterSceneByIdAsync(sceneId)`，命中缓存即复用。
  实测复用耗时 **0.01 秒**（首次生成约 14 秒）。

## 10. 存档与行为日志

**存档**（`SaveService` → `persistentDataPath/EpicSpark/saves/session.json`，tmp + move 原子写入）

| 字段 | 内容 |
|---|---|
| `userEvent` | 玩家输入的历史事件 |
| `currentSceneId` / `knownScenes[]` | 当前场景 + 已生成过的场景定义（复用与读档都靠它） |
| `gameMinutes` | 游戏内时间（`GameClock`） |
| `playerHp` / `heldTool` | 玩家血量与手持工具 |
| `visitedSceneIds[]` | 走过的场景 |
| `actionLog[]` | 最近 300 条行为记录 |

写入时机：每次锚点推进结束、应用退出。读档由标题界面「继续上次存档」触发，
`GameDirector.ResumeAsync` 恢复时钟、把历史行为灌回 `GameLog`、按 sceneId 重建场景并恢复玩家状态。

**行为日志**（`GameLog` → `persistentDataPath/EpicSpark/logs/<会话>/actions.jsonl`）

设计文档要求「玩家在场景中的所有操作及关联影响都被日志记录并打印」，当前覆盖：

| 事件 | 来源 |
|---|---|
| `attack` / `fire` / `reload` | 玩家控制器、枪械 |
| `damage` / `npc_hurt` / `npc_dead` | 玩家受伤、NPC 血条与死亡 |
| `talk` / `talk_summary` | NPC 对话开始与事后第三人称摘要 |
| `equip` | 工具切换（NPC 初始装备走 `EquipSilent`，不污染日志） |
| `enter_anchor` / `game_over` | 锚点推进、结局 |

日志同时进入内存环形缓冲（上限 4000 条），`GameLog.Recent(sceneId, n)` 会被塞进
`StoryContinueRequest.recentActions`——这就是剧情 Agent「读日志推断玩家意图」的接口。

## 11. 离线兜底矩阵

| 能力 | 有远端 | 无远端 / 失败 |
|---|---|---|
| 知识检索 | 远端 Embedding + 重排 | 本地 1024 维特征哈希 + 本地重排（600 事件全部可用） |
| 剧情 | 工具调用 → 纯 JSON → 校验补全 | 确定性五幕剧情构建器 |
| 灰盒 | 多轮工具调用（≤10 轮）→ 清洗 → 补齐 → 校验 | 确定性规划器（可复现 seed） |
| 模型检索 | 远端 Embedding | 本地向量 + 双语概念匹配 |
| 新资产 | z-image-turbo → RMBG-2.0 → Hunyuan3D-2 | 克隆库内最接近条目，写 runtime_library.json 并热注册 |
| NPC 对话 | LLM 人格化回复 + 总结 | 8 类 tag 的兜底台词池，轮换出词 |

### 12.3 端到端冒烟（离线、真实 Play Mode）

```
Unity.exe -batchmode -projectPath <工程> \
  -executeMethod EpicSpark.EditorTools.EpicSparkSmokeTest.Run -logFile Logs\smoke.log
```

五个阶段：进入 Play Mode → 自动以「攻占巴士底狱」开局 → 等首场景装配完成 → 触发首个锚点 →

| 指标 | 结果 |

## 14. 已知限制

1. **远端链路未联调**：本机没有 API Key，远端（ai.gitee.com）的 embedding / 工具调用 / 文生图 / 生 3D 只做了协议实现与失败降级，
   真实端点参数可能需要按实际服务调整。现在可以直接在游戏内设置界面（F10）填 Key 与模型名实测，无需改代码；
   默认值集中在 `ApiConfig`、`OpenAISettings`、`KnowledgeSettings`、`AssetGenSettings`。
2. **NPC 无角色模型**：美术库 43 个资产全是建筑/道具/武器/器皿，没有人形角色，NPC 用胶囊占位 + 名字与血条表示。
3. **容忍度滑块只影响资产复用**，不影响剧情与灰盒。
4. 43 个 GLB 每个约 4 万三角面、贴图内嵌 1.6–5.4 MB，全部解析耗时与内存较高；当前已按文件名缓存，重复使用不再解析。
5. 生成资产写入 `persistentDataPath/EpicSpark/generated/` 与 `runtime_library.json`（上限 400 条），不写回 StreamingAssets。

## 15. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 卡在「检索历史知识库」数分钟 | 旧版本会把 3606 个文本块全量丢给远端 `/embeddings` 建索引（226 次请求） | 已修复：默认本地向量；确认「知识库远端向量」是关的。见 §2 |
| 卡在「剧情&核心 Agent 正在推理…」很久 | 推理型模型（DeepSeek-R1/V4 等）会先输出大段思维链，单次可能 30–90 s | 调大「请求超时(秒)」，或换非推理模型；超时后会自动用确定性剧情兜底继续，不会卡死 |
| 日志出现「正文为空（finish_reason=length…）」 | `max_tokens` 被思维链吃光，正文没开始 | 调大 `max_tokens`（默认 4096，建议推理模型 ≥ 4096） |
| 测试连接报 401 / 403 | Key 与端点不匹配 | 用「测试连接」确认；DeepSeek 官方 Key 只能配 `https://api.deepseek.com/v1` |
| 测试连接报 404 | Base URL 路径不对（缺 `/v1`）或模型名写错 | 端点应形如 `https://host/v1`，模型名用服务商文档里的原名 |
| 对话 OK 但向量失败 | 该服务商没有 `/embeddings`（如 DeepSeek 官方） | 保持「知识库远端向量」关闭；知识库本就能全本地运行 |
| 生成资产全部是「兜底克隆」 | 服务商没有文生图 / 生 3D 接口 | 正常降级，用库内最接近的模型代替 |

### 一局游戏要等多久（实测）

一次开局 = 知识库检索（本地，1–2 s）+ 剧情 1 幕 + 灰盒规划 + 搭建（本地）+ 必要时资产生成。
远端只发生在剧情与灰盒两步。

同一网关（`ai.gitee.com/v1`，同一把 Key，2026-11 实测，小任务）两个模型的速度：

| 模型 | 输出 token | 耗时 | 速度 |
|---|---|---|---|
| `DeepSeek-V4.1-Flash-1017` | 695 | 6.5 s | **≈107 tok/s** |
| `Qwen3-32B` | 452 | 51.1 s | ≈8.8 tok/s |

结论：**V4.1-Flash 每一 token 并不慢，慢的是"请求次数"与"输出长度"**。两个吃时间的地方已经修掉：

1. 剧情的 `RequestTurnAsync` 原来**先试工具调用、失败再发一次纯 JSON**，推理模型常把整幕 JSON 塞坏在
   `tool_calls.arguments` 里，于是一次开局要付两次完整生成（实测 83 s）。现在剧情默认 `EnableTools = false`，只发一次。
2. 灰盒原来最多 **10 轮**工具调用，每轮都是一次完整请求（推理模型一轮 20–60 s）。现在默认 **2 轮**、
   整体预算 **30 s**，超时立刻用确定性规划，不再出现"灰盒超时 → 生成失败"。

当前每步耐心上限（可在设置界面调「请求超时」联动）：

| 步骤 | 预算 | 超时后 |
|---|---|---|
| 知识库检索 | 15 s | 空上下文继续（本地检索通常 1–2 s） |
| 剧情 1 幕 | 请求超时（默认 90 s） | 确定性剧情 |
| 灰盒规划 | 请求超时 ÷ 3，夹在 20–45 s（默认 30 s） | 确定性规划 |
| 搭建 | 本地，无网络 | — |

实测观感：用 `DeepSeek-V4.1-Flash-1017` 一局首次生成约 30–60 s；换非推理的轻量模型可到 10–20 s。

- Unity 编辑器日志：`%LOCALAPPDATA%\Unity\Editor\Editor.log`（`[启动]` / `[知识库]` / `[导演]` / `[行为]` 前缀是关键字）
- 游戏行为日志：`%USERPROFILE%\AppData\LocalLow\DefaultCompany\epicsparktest4\EpicSpark\logs\<会话>\actions.jsonl`
- 存档：同目录 `saves\session.json`；生成资产：`generated\`；运行期模型库：`runtime_library.json`

## 场景生成调试录制（排查"场景像乱拼"用）

每轮场景生成都会在本地落一份完整记录，默认开启，游戏内按 **F11** 可开关。

目录：`persistentDataPath/EpicSpark/debug/<时间戳>_<sceneId>/`
（Windows 实际路径：`C:\Users\<用户>\AppData\LocalLow\DefaultCompany\epicsparktest4\EpicSpark\debug\`）

| 文件 | 内容 |
| --- | --- |
| `00_信息.txt` / `00_概要.txt` | 时间戳、场景 id、布局文本长度等概览 |
| `01_剧情提示词.txt` | 剧情&核心 Agent 的 system + user 提示词全文 |
| `02_剧情原始输出.txt` | 模型返回的原始文本（JSON 未解析版，含被修复前的残缺 JSON） |

| `04_场景JSON.txt` | 解析后的 `SceneSpec`（锚点/道具/流程/尺寸/出生点） |
| `05_布局详细描述.txt` | 叙述 + `layoutDescription`（地编依据的原始中文描述） |

排查顺序建议：

1. 先看 `05_布局详细描述.txt` —— 剧情有没有写出坐标？没有的话后面必然乱；
2. 再看 `06_灰盒规划JSON.txt` 的 `plannerNote` —— 是"剧情布局地编"还是回退到了 archetype 网格；
3. 对比 `07` 与 `09` 两张图 —— 灰盒规划的东西，拼装后还在同一位置吗；
4. 查 `08_搭建结果JSON.txt` 的相似度 —— 建筑槽是否被匹配成了石阶/水桶这类小道具。
